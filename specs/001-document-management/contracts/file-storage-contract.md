# File Storage Contract

## Purpose

This contract describes the internal file storage abstraction used by the document management feature. It is designed to keep document upload logic independent from the underlying persistence mechanism while staying compatible with the repository’s offline training model.

## Interface Contract

The application should expose a storage abstraction with the following responsibilities:

- `UploadAsync(...)`: save a file stream and return a safe storage key or relative path
- `DeleteAsync(...)`: remove the stored file for the given storage key
- `DownloadAsync(...)`: return a stream for authorized access
- `GetUrlAsync(...)`: resolve a safe path or URL when the caller needs a download or preview reference

## Required Invariants

- The storage key must be generated by the application, not by user input.
- The implementation must enforce file-type and size validation before writing.
- No user-supplied filename may be used directly in the storage path.
- Files must be stored outside `wwwroot` to prevent direct web exposure.
- The application must authorize the caller before returning the file stream or URL.

## Local Implementation Assumptions

- Use a local folder such as `AppData/uploads/{userId}/{projectId or personal}/{guid}.{extension}`.
- Keep the metadata in the database so the document can be queried, searched, and filtered.
- Preserve the same contract if a future Azure storage implementation is introduced through dependency injection.

## Contract Boundary

This contract is internal to the application and does not require a public API or network endpoint. It is intended to isolate storage concerns from UI and business logic in a way that supports future migration without forcing a rewrite of the document feature.
